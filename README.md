# harness-kit

**A ledger-based safety net for multi-agent coding pipelines — where the ledger, not the agent, is the source of truth.**

一个三方协作（教练出卡判卡 / 编码执行 / 人做中继与签字）的防失控骨架。
不靠更长的提示词约束模型，靠一份可核对的账本。

---

## 它解决什么问题

让 AI 写代码，真正难的不是「写不出来」，是**你无法确认它做的是不是它说的事**：

- 它说「测试通过」——哪条命令、什么输出、能不能复现？
- 它说「这一步完成了」——判定依据是什么，还是它自己觉得？
- 它改了文件——谁允许的，签名了吗，还能回到上一状态吗？
- 换个会话继续——上一轮的结论还在吗，还是全靠人转述？

本包的回答是：**把所有可以变成事实的东西变成事实，剩下的一律当意见。**

---

## 三条核心主张

**1. 账本是唯一事实源**

`events.jsonl` 是 append-only 的哈希链（`seq` / `prev` / `self` 三字段自校验）。
状态、注意力、审计、下一张卡该做什么——全部从账本**派生**，没有一个 agent 可以声明。

> agent 过去全部声明过 `done: true` / `verified: true` / `health: green`，所以这些现在全部由脚本算。

**2. 只有人能签字**

`stage-add`（把一步写入计划）、L2/L3 的 `sign-gate`、以及最终的 `seal`，只有人能签。
`stage-edit` / verify / finish-step / 合并这些日常动作不需要签名——**签字只放在真正不可逆的地方**。

**3. 门只提示，不阻断**

结构红线（文件 ≤400 行 / 函数 ≤60 行 / 嵌套 ≤4 层）是一份**报告**，不是闸门：

- 任何情况退出码都是 `0`，不进 PASS/FAIL
- 老代码按上一步已验收状态做棘轮，只在原地变胖时提示
- 每类明细封顶 8 条，存量问题只留计数，**报告长度有上界**
- 不需要写豁免、不需要清理历史、不需要任何人多做一件事

> 硬限制会把模型逼到「凑数拆分」和反复请示。提示让它自己判断，人只看值得看的那几行。

## 包里有什么

| 目录 | 内容 |
|---|---|
| `kit/derive/` | 34 个安全网脚本：账本写入、校验、审计、状态派生、封锚、canary |
| `kit/hooks/` | Claude Code 的 pre/post tool hook + 决策守卫（非 Claude 宿主诚实降级为轮询补账） |
| `kit/contracts/` | 交接卡与任务卡的 schema |
| `kit/checks/` | 结构红线报告 `size_gate.py` + 它的 26 条反证 |
| `kit/prompts/` | 教练与编码两个角色的行为基线（人格母本） |
| `kit/policy/`、`kit/rules/` | 政策层草案与宪法。**这一层不承诺可复现**，是裁定起点不是保证 |
| `examples/` | 真实项目的完整实战案例：1334 条账本、6 轮独立观测、故障复盘 |

`ARCHITECTURE.md` 是整个机制的完整设计说明（为什么这样切、每条规则的来历、被删掉的设计和原因）。

## 快速开始

```powershell
# 需要 Windows + PowerShell 7 + Node
pwsh -File kit\install.ps1 -ProjectRoot D:\my-project -By "你的名字"
```

安装器会核对 MANIFEST 全部哈希、部署脚本与 hooks、初始化账本、写 genesis 锚、然后跑 canary 与审计。
**同版本环境下逐字节可复现**；对不上会在第 1 步就停，不会带着不确定继续。

也可以把 `kit\` 整个给一个 agent，让它读 `kit\INSTALL-AGENT.md` 自行安装。

## 已知限制（写在这里而不是藏在问题里）

- **Windows-only**（Linux 理论可跑、未实测）
- **单用户单机**：账本锁是同盘 create-exclusive，两台机器并发追加 = 断链
- **hook 全功能仅 Claude Code**：其他宿主降级为轮询 + 补账，不给未验证的通用模板
- 政策层（`policy/`）跨 LLM 不保证可复现，依赖人中继观测
- 依赖仅 pwsh 7 + node，零外部安装

## 它和别的项目有什么不同

2026 年这条线上已经有不少项目在解决同一个问题。我看到的（截至 2026-11）：

| 项目 | 做法 | 与这里的关键差别 |
|---|---|---|
| [vibey](https://github.com/the-vibey-project/vibey) | 编排器 + **PostgreSQL** 的 append-only 账本 + 人工把关的 review | 账本在数据库里；这里是**仓库内的纯文件**，可 git 管理、可离线核对、可逐字节验证 |
| [vibecheck-linear-jev](https://github.com/mgd34msu/vibecheck-linear-jev) | 以 **Linear issue** 为工作账本，判定模型检查 agent 的汇报 | 依赖外部 SaaS；这里**零外部服务** |
| [vibecoding-orchestration](https://github.com/qi-mouren/vibecoding-orchestration) | 闸门 G0–G5 + 契约冻结 + 多 agent 编排 | 闸门是**阻断式**；这里的门**只提示不阻断**，签字只放在不可逆动作上 |
| [spec-driven-development](https://github.com/znck/spec-driven-development) | 先写规格、再写代码 | 管的是"写之前"；这里管**"写的过程中到底发生了什么"** |

**共同的问题**：agent 说自己做完了，凭什么信？
**分歧的地方**：账本放在哪、谁有权签字、不达标时是拦还是提示。这三点决定了遇到分歧时谁说了算。

## FAQ

**这是又一个 prompt 模板吗？**
不是。prompt 管"告诉模型该怎么做"，这里管"事后怎么确认它真做了"。核心是一份可核对的账本，提示词只是附属。

**为什么不直接用 git 提交历史？**
git 记的是"文件变成了什么样"，不记"谁批准了这一步、证据是什么、失败了几次、为什么偏离计划"。账本记的是决策与证据；git 只是它的一个执行手段。

**agent 能不能伪造账本？**
它是 append-only 的链，每条带 `prev` 和 `self` 哈希，改任何一条都会断链，`verify-ledger` 立刻发现。但真正的答案更实在：**没人需要信账本，因为它不产生权力**——签字权在人手里，账本只负责让"发生了什么"无法被含糊过去。

**必须用 Claude Code 吗？**
不是。hook 全功能需要 Claude Code；其他宿主降级成"轮询 + 补账"，功能少但一致。账本和签名机制与宿主无关。

**为什么只支持 Windows？**
它就是这么长出来的——真实项目在 Windows 上跑。Linux 理论可移植（差异集中在计划任务和 console 编码），但没测过，所以不承诺。

**会不会拖慢开发？**
日常动作（改卡、验证、收步、合并）都不需要签名。签字只放在三处不可逆的地方：把一步写进计划、高风险步骤的放行、最终封锚。

**为什么结构检查不阻断？**
硬限制会把模型逼成"凑数拆分"——文件切得更小、函数更短、可读性更差，还增加反复请示。所以它降级成报告：告诉你哪里胖了，怎么处理你自己判断。**门只放在真出事的地方。**

**能不能只用一部分？**
能。账本 + 收步 + 状态派生是一组；签名是一组；结构报告独立。最小可用形态是"账本 + 一个能跑的证据命令"。

## 术语

| 词 | 含义 |
|---|---|
| **账本** (ledger) | `events.jsonl`，append-only 的哈希链，唯一事实源 |
| **事件** (event) | 账本的一行：验证、偏离、跳过、闸门、封锚、步进、文件删除…… |
| **锚** (anchor) / **封锚** (seal) | 给人看的一段哈希，钉住某个时刻的全部机制文件；改了就重算，用于发现"安全网自己被改了" |
| **卡** (stage / card) | 一步的工作定义：目标、产物、验证命令、风险级别 |
| **交接卡** (handoff) | 编码每步结束的输出：产出、决定、偏离、不确定、遗留。**是沟通物，不是事实源** |
| **派生视图** (derived view) | 从账本算出来的状态。agent 不许声明，只许被算出来 |
| **检测器** (detector) | `T*` 管时序与一致性，`C*` 管契约漂移。命中就进注意力队列 |
| **门** (gate) | 判定点。这里的门分两种：**签字的门**（阻断，只有人能过）和**结构的门**（只提示，不拦） |
| **canary** | 安全网自己的回归测试集：把历史事故变成场景，改动后必须先全绿 |

## 它换来了什么

不是一个 PPT 方法论，是一个真实业务项目跑了 1000+ 步之后沉淀的形态：

- **1334 条实账**，含安全网自身死亡的那次事故
- **6 轮独立观测**：每轮由不知情的观察者从账本反推「这一步发生了什么」
- 每一起踩过的坑都变成了一个 canary 场景或一条检测器——**包括把并发写、断链、误签、无解释写入变红**

`examples/` 里的案例已脱敏（业务名、域名、品牌、路径全部替换），但**账本结构、检测器输出、故障时间线一字未改**。
